# incremental-sync-python

本地可验证的增量数据同步：用本地文件模拟上游数据源与目标端，不依赖任何外部
服务、真实凭据或网络资源。在**重复投递、乱序到达、并发提交、进程重启、表结构
演进**下，目标端最终状态可预期且可复现；上游按业务事务推送时，同一事务的
多条变更（可跨表）**整体生效、原子可见**。

## 组件

| 模块 | 职责 |
| --- | --- |
| `sync/models.py` | 变更记录 `ChangeRecord`（含 `tx_id`/`tx_total`）、表结构 `TableSchema`、拒绝原因 `RejectReason`、事务拒绝 `TxRejection` |
| `sync/source.py` | 上游模拟：JSONL 变更日志，seq 从 1 严格递增、无空洞（乱序 append 直接报错） |
| `sync/target.py` | 目标端模拟：本地 JSON 行存储；`apply_atomic` 在单锁内执行一批写入并一次落盘 |
| `sync/checkpoint.py` | 位点持久化；回退与跳段抛 `CheckpointError` |
| `sync/schema_registry.py` | 表结构注册与兼容演进；不兼容变化抛 `SchemaIncompatibleError` |
| `sync/txn.py` | 事务缓冲：按 `tx_id` 分组、按 `tx_total` 判定凑齐、可序列化 |
| `sync/rejections.py` | 被拒事务的持久化留存（按 `tx_id` 幂等，可事后查看） |
| `sync/applier.py` | 核心：幂等应用、乱序归并、事务整体生效/整体拒绝、位点推进、状态持久化 |
| `sync/pipeline.py` | `run_once`：从已确认位点读一批并应用，重复调用安全 |
| `main.py` | FastAPI 演示接口（状态落在 `./data/`，纯本地） |

## 同步语义

**位点（seq）**：源端为每条变更分配从 1 开始严格递增、无空洞的序号。
已确认位点 = 目标端已连续应用的最大 seq。

**最终一致性保证**：同一批变更无论被重复投递、乱序到达还是多线程并发提交，
目标端最终状态与“按 seq 顺序只投递一次”完全一致。机制：

- **幂等去重**：`seq <= 已确认位点`、已在未确认集合或已缓冲在事务中的记录
  判为重复，跳过。
- **乱序归并**：按 `(table, pk)` 维护高水位（已应用的最大 seq），过期记录跳过，
  保证每个主键的最终值由最大 seq 的变更决定。
- **位点连续推进**：确认位点只推进到连续前缀；存在空洞时停在空洞前等待补齐，
  绝不跳过空洞从中间状态继续。
- **崩溃恢复**：已确认位点、未确认 seq 集合、键高水位、事务缓冲全部持久化，
  重启后从已确认位点继续；已确认部分的重复投递被识别为重复，不重复应用、不丢失。

## 事务化同步

上游按业务事务推送：一次业务操作产生的多条变更（可跨表）携带同一个
`tx_id`，且每条事务记录声明该事务的记录总条数 `tx_total`。

**凑齐判定**：缓冲中某事务的已见条数（含被单独消费的过期记录）达到
`tx_total` 即视为凑齐。不依赖“最后一条”标记，因此记录任意乱序、
任意分批到达都能正确判定；事务之间在位点流中交错也不受影响。

**原子可见性范围**：事务凑齐后，其全部行变更在目标端的同一把锁内执行并
一次落盘（`LocalTarget.apply_atomic`）。任何时刻从目标端读取（`get`/`rows`），
只能看到该事务**全部生效前**或**全部生效后**的状态，绝看不到“改了一半”。
未凑齐的事务只存在于应用器缓冲中，对目标端完全不可见。可见性的边界是
目标端存储本身——本实现中是整个 `LocalTarget`。

**整体拒绝**：事务凑齐后先对组内每条记录做确定性校验（结构版本、未知表、
必填字段、类型），再按 seq 顺序在“目标端 + 事务内效果”上演练主键语义。
任一记录非法，则**整个事务被拒绝**：一条都不写入，全部 seq 计入已消费
（死信），位点可越过。拒绝结论确定且稳定——同样内容重投结论相同。
被拒事务连同全部记录完整留存到 `rejections.json`（按 `tx_id` 幂等，
不重复留存），可事后查看。

**暂时性阻塞**：事务内 update/delete 的目标行尚不存在（通常是它依赖的
前序事务还没生效）时，该事务不消费、留在缓冲，后续任何一批到达都会
自动重试；依赖生效后事务即可整体应用。位点停在该事务之前，绝不跳过。

## 失败与恢复

**持久化顺序**：每批处理结束后按 数据（`target.json`）→ 应用器状态
（未确认集合、键高水位、事务缓冲，`applier_state.json`）→ 位点
（`checkpoint.json`）的顺序落盘，位点永远是最后一步，因此**读到的位点
绝不超过已经真正生效的数据**。被拒事务的留存在数据落盘前写入，且按
`tx_id` 幂等，崩溃重放不会产生重复或矛盾的留存。

**进程中途被杀/写盘报错后重启**：

- 崩溃发生在数据落盘前：什么都不算发生，从已确认位点重新投递即可。
- 崩溃发生在数据落盘后、位点提交前：重启后重复投递的记录被未确认集合/
  键高水位识别为重复（insert 撞上一致内容也判为幂等重复），位点补齐，
  **不多写、不漏写**。
- 事务未凑齐时崩溃：缓冲已持久化，重启后目标端仍无中间态，剩余记录
  到达后整体生效。

**位点回退与跳段**：照旧明确拒绝（`CheckpointError`），进程重启后不会
从中间状态继续。

## 拒绝语义（不静默丢弃）

非法记录进入 `ApplyResult.rejected`（单条）或 `ApplyResult.rejected_txs`
（整个事务），原因可区分：

| 原因 | 含义 | 是否消费 |
| --- | --- | --- |
| `PK_CONFLICT` | insert 已存在的主键（确定性，死信）；或 update/delete 不存在的主键（**暂时性**，可能乱序/前序事务未生效，等待重投，位点不前进） | 前者消费，后者不消费 |
| `MISSING_FIELD` | 必填（非空且无缺省）字段缺失或为 null | 消费（死信） |
| `TYPE_MISMATCH` | 字段类型与表结构不符（`bool` 与 `int` 严格区分） | 消费（死信） |
| `UNKNOWN_TABLE` | 表未注册 | 消费（死信） |
| `SCHEMA_INCOMPATIBLE` | 记录结构版本高于当前，或字段不在当前结构中 | 消费（死信） |

死信类拒绝是确定性的（同记录/同事务重投结论相同），因此计入已消费、
位点可越过；暂时性主键冲突不消费，位点停在该处，待缺失的前序变更
到达后重投成功。事务场景下，任一记录的确定性拒绝会升级为整个事务的
`TxRejection`；暂时性冲突则让整个事务等待重试。

## 结构兼容规则

- **新增列：兼容**。缺省语义确定且稳定——以列定义的 `default` 为准（未给为
  `None`）；旧版本记录应用时按缺省补齐新列；已存在的旧行**不被追溯改写**
  （不静默回填），读取方按当前结构自行补缺省。
- **删列、改名（= 旧列消失 + 新列出现）、改类型/可空性：不兼容**。
  `SchemaRegistry.evolve` 抛 `SchemaIncompatibleError`，结构版本不前进，
  绝不静默接受。
- 记录携带当前结构中不存在的字段 → 按 `SCHEMA_INCOMPATIBLE` 拒绝，
  不发生错列/错位写入。

## 边界条件

- 位点回退（`seq <= 已确认`）与跳段（声明的前驱与持久化位点不一致）一律
  `CheckpointError`，进程重启后不会从中间状态继续。
- 源端 append 非连续 seq 直接 `ValueError`，保证“位点之后继续读”良定义。
- 永久空洞（某 seq 的变更永远不到达）会使位点停在空洞前——这是有意的
  at-least-once 语义，需要运维介入，而不是静默跳过。
- 事务永远凑不齐（`tx_total` 与实际投递不符）同理：事务不生效、位点停在
  事务之前，等待运维介入。
- 主键在目标端统一按 `str` 规范化比较。

## 本地验证

```bash
uv run pytest tests/ -q        # 全部测试（日志含位点与变更流水）
uv run pytest tests/ -q -s     # 实时打印 applied/dup/reject/tx/checkpoint 日志
```

测试覆盖：重复投递、乱序到达、并发提交（多线程重叠批次）、重启续传、
位点回退/跳段拒绝、五类拒绝原因区分、新增列缺省语义、删列/改名/改类型拒绝、
端到端管线，以及事务场景：跨表整体生效与原子可见（含并发读者）、事务的
重复投递/乱序分批/并发提交、组内单条非法导致整个事务回滚并留存、
暂时性阻塞自动重试、提交过程中出错后重启续传（`tests/test_*.py`）。

```bash
uv run uvicorn main:app --port 8000
curl -X POST localhost:8000/sync/run   # 从已确认位点同步一批，幂等
curl localhost:8000/sync/status        # 查看位点与目标端数据
```
